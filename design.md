# gclic: design notes

gclic stands for git cli companion. It was first called mygc.

## Original brief

**Goal:** build a TUI git client in Rust.

**Subgoal:** learn Rust in the process.

**Design constraint:** the codebase must stay simple and easy to follow. The author must grow with the project.

**Scope:** this is not a complete client. git's CLI is great for many use cases, but for some things a TUI saves a lot of time or does what the CLI simply cannot. Four features are in scope:

1. **Visual staging area and commit.** Browse changed files, stage or unstage them, or one change of them at a time, restore unstaged files or changes, and commit whatever is staged. Any file's diff can be opened in a split view. It should mimic VS Code's git panel staging area, with a TUI flavour and vim-style keyboard navigation.
2. **Branch viewer**, inspired by VS Code's Git Graph, below the staging area.
   - By default it shows the current branch and its remote version, e.g. `feature` and `origin/feature`.
   - Nice, light visuals rather than a cluttered log-like list: a commit chain where each commit is a bead and beads are joined by lines, with a change of color at the transition between local and origin.
   - Commits are navigable by keyboard. Opening one shows its changed files, and opening a file shows its diff.
   - A box with the commit message and metadata can be toggled, and the commit sha can be copied to the clipboard.
   - Any number of branches, local or remote, can be selected to render instead of the default two.
3. **Branch picker.** List existing branches, fuzzy search or scroll to select one, and check it out.
4. **Differ of two arbitrary refs.** Select two refs. The view shows how many commits A is ahead of and behind B since their common ancestor, and a navigable list of differing files. Opening one shows a split diff.

**Approach:** the features are fairly separate, so they can advance modularly, one at a time, starting with 1 and 2. Before going in seriously, one-shot the entire tool as an MVP, then use it to refine what we want and implement it for real, feature by feature.

## Where it stands

The MVP is feature complete, and on macOS it's a fully working app: every feature in the brief is in, along with what using it asked for. A rewrite from here would be a learning exercise and an architecture review, not a feature project. The notes below describe what was built, so they can serve as its starting point.

The approved MVP plan and the first round of feedback on it are in git history: see `design.md` as of commit `ecb4f54`.

## What it looks like

Two tabs, `Repo` and `Compare`, switched with `tab`. A hint bar at the bottom lists the keys that apply right now, with `? help · q quit` after them.

- **Repo:** a left column of three panes, Branches, Changes and Graph, moved between with `h`/`l`. Their heights follow focus: Branches shows only the checked-out branch until focused, Changes fits its files, and the graph takes the rest. The panes `h` and `l` lead to are marked `[h]` and `[l]` after their titles.
- **Compare:** how two refs differ, started with `c` from Branches, the graph or the tab itself.
- **The right side:** a preview that takes 80% of the width when open, either a diff or a commit's details, never both. Each stays in its mode: moving onto a commit leaves a diff alone, and moving onto a file leaves the details alone (a file shows its own commit's details). `enter` on a file shows its diff, a second `enter` moves into it, and `esc` comes back, then closes it. `z` zooms it to the full width.
- **Popups:** a title saying what they are, and their keys in the bottom border. Keys are yellow, and the key for a destructive action (discard, delete, close a comparison, quit) is bold red. Borders are cyan, except git errors, which are red.

## How it's built

Dependencies: `ratatui` (with crossterm), `anyhow`, and `syntect`, with its pure-Rust regex engine. Dependencies are optimised even in debug builds, since highlighting is too slow otherwise. The theme, `assets/vscode-dark-modern.tmTheme`, holds VS Code's Dark Modern colours, as Zed's "VSCode Dark Modern" theme has them.

### Patterns worth keeping

- **Panels return actions.** Each pane has `handle_key(key) -> Action` and `render(frame, area, focused)`. Panes never touch each other: they return an `Action` (`OpenDiff`, `PreviewDiff`, `Refresh`, `Compare`…), and `App::apply` carries it out. This avoided most fights with the borrow checker.
- **`git.rs` is the only place that knows git is a subprocess.** Everything else gets typed data. Its commands are made in one place, `command`, and run by `output`: with no stdin, so nothing can wait for hidden input, and with `GIT_OPTIONAL_LOCKS=0`, so reads don't take the index lock. Only the commands typed after `:git` are set up otherwise, as they take locks as git normally does.
- **Each pane gives its own key hints**, as (key, action) pairs next to its `handle_key`, and a test checks each one is in the help.
- **Lists and text share their movement:** `ui::Cursor` for every list but the graph's, and `ui::Scroll` for the help, `:git` output and commit details.
- **`DiffSource`** names where a diff comes from (unstaged, staged, untracked, conflict, a commit, two refs), so one diff pane serves every feature.
- **Pure functions for the hard parts**, unit tested without a terminal: the graph's lane layout, diff parsing, line pairing, word marks, conflict parsing, the fuzzy matcher.

### Concurrency

- **The worker thread** (`worker.rs`) does the slow reads: the auto-refresh poll (the refs fingerprint, `git status`, the open diff), which carries on under popups, as they only cover part of the screen, a commit's size for its details, and syntax highlighting. The UI hands it jobs through a small queue and picks up results from a channel every 30 ms, so keys never wait for it. The screen is drawn only when something changed: a key, a result, a command or fetch ending, or the fetch note's "10s ago" moving on.
- **Refreshing by key presses:** each poll starts a few git processes, about 30–50 ms of CPU, so gclic polls every second while in use and every 10 s once no key has been pressed for 30 s, and the first key after that polls at once. Idle, gclic and its git processes take about 0.5–0.7% of a core, a minute's fetch included, down from 7–11% polling every 500 ms (#68, #77).
- **Only reads happen on it.** Anything that changes the repo, and the full refresh after it, stays on the UI thread, in order, so a change shows at once.
- **Stale results are dropped:** each full refresh bumps a generation counter, and a poll asked for before the latest refresh is ignored. Colours only apply to the exact diff text they were made from.
- **Short-lived parallelism** with `std::thread::scope`: the panes' refreshes, the graph's log and unpushed check, a poll's git calls, a comparison's refresh, and the two file versions read for highlighting, and their colourings, all run at once.

### Speed

Most of the time goes into starting git processes and into highlighting. Measured on the author's Mac, release builds:

- A full refresh takes about 15 ms, down from 45 ms: the branch list is fetched once, refs are resolved in one `rev-parse`, the checked-out branch is read from `.git/HEAD`, and the rest runs in parallel.
- Moving between files with a diff open takes about 1 ms until the redraw starts, since the diffs one key away (`j`, `k`, `g`, `G`, and `r` in Compare) are prefetched and coloured into a cache of up to 20,000 rows, and shown from it without asking git.
- Colouring both sides of a diff at once, rather than one after the other, takes about 40% less time: 120 ms rather than 200 ms for a 1,750-line Rust file.
- Moving through the graph with its details open takes about 10 ms a commit, as its message shows at once and its size, which git counts as long as the diff takes, comes from the worker: on a commit of 3,000 files, that's 400 ms the keys no longer wait for.
- Memory is about 24 MB, most of it syntect's grammars.

The measuring scripts lived in the git-ignored `target/bench/`. `docs/screenshots.py` shows how to drive gclic in a pseudo-terminal and read its screen.

### Git edge cases

- **Merge conflicts:** a conflicted file previews as its two sides, read from its conflict markers, with the file's own line numbers so `o` opens the editor on the conflict. A diff3 base section is skipped. `d` isn't offered on it, and the Changes title says when a merge, rebase, cherry-pick or revert is in progress. Conflicted files get their own section at the top of the Changes pane, as VS Code's "Merge Changes", shown only while there are any.
- **Worktrees:** a branch checked out in another worktree shows `in ../name` and can't be checked out here. gclic stays in the worktree it started in.
- **Submodules:** shown as one changed entry with git's "Subproject commit" diff. `d` isn't offered, as a plain restore doesn't touch them.

### Platform assumptions

- The clipboard goes through `arboard`, which works on macOS, Windows and Linux.
- The graph's beads are the branch-drawing characters (U+F5EE to U+F60D) in Ghostty and kitty, which draw them themselves, told apart by `TERM_PROGRAM` and `TERM`. WezTerm draws them only in nightly builds (since its PR #6873, April 2025), so it isn't detected. Elsewhere they're plain `●`/`○`, whose lines don't reach them.
- `o` opens the editor named by `$GCLIC_EDITOR`, `$VISUAL` or `$EDITOR`, with the line given the way each common editor takes it, and says so if it isn't on the `PATH`.
- The code is formatted with `cargo fmt`, at rustfmt's defaults, and CI (`.github/workflows/ci.yml`) checks it, then runs clippy and the tests on macOS and Windows. The commit that first formatted it is in `.git-blame-ignore-revs`, for `git blame` to skip. Pushing a version tag such as `v0.2.0` runs the release workflow (`release.yml`): it checks the tag against `Cargo.toml` and publishes a Windows zip as a GitHub Release.

## Decisions, and why

- **Graph: one row per commit.** Beads are branch-drawing characters with lines to their cell's edges, so consecutive beads join without spacer rows, and forks and joins sit on the bead's row (`●─╮`). A commit takes the colour of the first ref reaching it, trying refs with no commits of their own first, so whichever side is ahead shows in its own colour. Unpushed commits are hollow.
- **The preview is entered, not tabbed to.** `h`/`l` stay free for scrolling inside a diff, and moving through a list with the preview open is the common case.
- **The hint bar is contextual.** It only lists what applies, the key for a destructive action is red in popups, and global keys come last after a separator.
- **Line pairing by similarity.** Removed and added lines pair to maximise their total similarity in order, so an added line doesn't shift every pair below it. Positional pairing breaks the word marks as soon as a change adds a line.
- **Compare is a tab.** It's a different view of the repo, not a pane, and the tab keeps a comparison around without losing it. `c` starts one from wherever you are, and closing it asks first.
- **Git's status letters, VS Code's colours.** `?` untracked and `U` conflicted, as git has them, coloured as VS Code's git panel colours files.
- **`o` opens the user's editor, and Neovim can host gclic.** The editor comes from the variables git reads. GUI editors start in the background; terminal ones get the terminal, as `:!` commands do, and quitting them comes back to gclic as it was. That starts a fresh editor each time, which is fine for an edit but not for reading code, where the language server and jump history should stay. So gclic also runs inside Neovim, through `lua/gclic.lua`, a small plugin that keeps it in a terminal, in a sidebar or a float, alive while hidden between uses. Inside Neovim, which `$NVIM` gives away, `o` asks that Neovim to open the file, through the plugin, and `:cd` changes its working folder, so the repo picked in gclic is the editor's project too. The plugin lives at the repo's root so the repo installs as a Neovim plugin.
- **Compare goes *from* one ref *to* another,** not *before* and *after*: a comparison is a trip through the commit graph, and the two refs need not be ordered in time.
- **Diffs are side by side or unified depending on the room,** side by side when each side gets 80 columns of text. `s` overrides that for the rest of the session. It used to stage in Changes too, as an alias of `space`, and gave that up to work from every pane. Unified is made from the same rows, each change's removed lines then its added ones, so pairing, word marks and colours carry over, and switching keeps the active row.
- **The minimap measures the file, not the diff,** so it looks the same with the whole file or just the changes, and shows where the hunks sit in it. The file's length comes free with highlighting, which reads both versions anyway, and until then the diff's last line stands in.
- **Rare operations are commands, not keys.** `:` opens a command line, so deliberate, occasional operations such as `:cd` don't use up single keys. It's also where running git commands from gclic would go.
- **Two ways to run a command.** `:git …` runs captured, in the background, with no terminal: the editor, credential prompts and SSH passphrases are turned off, so a command that would ask fails at once rather than hang or draw over the TUI, and its error says to use `:!`. It runs in its own process group, so `ctrl-c` stops the helpers git starts too. Otherwise `ctrl-c` quits, but asks first, as `q` does, since a `ctrl-c` meant for a command that has just ended would quit gclic. `:!…` gives the terminal to any command, as vim's `:!` does, which is how editors, `add -p` and passphrases work, without gclic emulating a terminal. gclic waits for enter only if the command printed something, which it tells by the cursor: full-screen programs restore it on exit, and printing moves it. The screen is cleared first, so printing can't scroll it back into place.
- **Fetching in the background, the one remote operation gclic does by itself.** Without it, the ahead/behind counts are only as fresh as the user's last fetch. Every minute, as lazygit does, and on startup and `:cd`, it fetches the remotes local branches track, each once, leaving other remotes to the user. It's best effort: no prompts, Git Credential Manager's sign-in window included, so it only works where signing in already happened. It skips the housekeeping a fetch may start and FETCH_HEAD, which belongs to the user's own fetches. It runs on a thread of its own, as it can take seconds, which would hold up the worker. A fetch that brought anything moves the remote refs, which the next poll sees, refreshing everything. `:autofetch off` stops it for the session. A fetch by hand is `:git fetch`, which is git's, with git's output and errors as any `:git` command has them. The Branches title says `fetching…` while it runs, and that it fetched once it works. The fetches every minute only say when one failed, as saying each time would flicker.
- **Inside Neovim, gclic takes the editor's colours.** The plugin passes the colour scheme's colours in `$GCLIC_EDITOR_COLORS`: the editor's background and text, its diff colours, and a colour for each kind of token. gclic draws its diffs in them, building a syntect theme that maps the TextMate scopes its grammars use onto Neovim's groups (`theme.rs`), so a diff looks like the buffer it opens into. Changed words get their line's tint with some of the text colour mixed in, as colour schemes rarely have a colour for them. The rest of gclic took the terminal's colours at first, so switching between the two still showed, but beside the code in a sidebar it looked out of place, so by default it takes the colour scheme's too: its window the editor's background and text, its 16 colours the colour scheme's terminal colours, and the selected line the colour scheme's for a list's selected item, `PmenuSel`'s background, passed in `$GCLIC_SELECTED_BG`. Not `CursorLine`'s, the obvious one, which colour schemes often keep barely off the background, as the editor's cursor and line number mark the line too, which gclic's lists have nothing like: in vscode.nvim it's `#222222` on `#1f1f1f`. `PmenuSel` is what Snacks's pickers and file tree use for their selected row too. A colour too close to the background is passed over, for `Visual`'s, then `CursorLine`'s, then gclic's grey. The diff's active line keeps the grey, as a list's blue drowns the code. The rest of the interface takes the editor's colour for the same thing, through `$GCLIC_UI_COLORS`: a pane's border `WinSeparator`'s, as windows are divided, and focused `FloatBorder`'s or the text's, as Snacks outlines its boxes; files' and lines' git colours the sign column's, `GitSignsAdd` and the like, or Neovim's `Added`, `Changed` and `Removed`; errors and destructive keys `DiagnosticError`'s and warnings `DiagnosticWarn`'s. gclic's one accent, cyan, for what's focused or selected, where to type and headings, takes the focused border's colour, so the selected tab, popups' borders and the diff's headings match the focused pane. Keys in hints and the graph's branches, which have no standard group, keep the palette's yellow and so on, which are the colour scheme's terminal colours anyway. A colour scheme's diff colours are opaque, and often so strong that they drown the code, where editors such as VS Code lay theirs over it translucent, as gclic's own imitate. So gclic takes their hue at its own strengths: lines as far from the background as its own tints, changed words as far as its own words, and never further than the colour scheme's colour. `colors = "terminal"` keeps the terminal's. Without the variables, diffs keep VS Code Dark Modern's colours and the selection a grey.
- **Neovim shows the repo in gclic's colour.** The plugin draws a bar across the top, as Neovim's tabline, in the repo's colour, with its folder and name as gclic's tab bar has them. The colour is worked out in one place, gclic's `accent.rs`, which `gclic --color` prints along with the repo's root, rather than again in Lua, where the two could drift apart. The plugin asks at startup and whenever Neovim's folder changes, gclic's `:cd` included, and gclic's `:color` tells the Neovim around it to ask again. Answers can come back out of order after quick changes of folder, so only the latest question's counts.
- **gclic follows Neovim's working folder too.** The plugin writes Neovim's working folder to a file named in `$GCLIC_FOLLOW` whenever it changes, and gclic, on its regular poll, switches to the repo that folder is in. A file rather than keys typed into gclic, which could land in a popup or a search, and gclic waits while one is open. Only the working folder counts, not the file being edited, so gclic doesn't change repo, and lose its state, for a glance at a file elsewhere. Following doesn't tell Neovim to `:cd` back, which would undo a move into a folder inside the repo, and gclic's own `:cd`, which does tell Neovim, comes back as the repo gclic is already in, so there's no loop.
- **In Neovim, gclic sits in a sidebar and goes over the whole editor when it has more to show** (#89). The sidebar is the Repo tab's panes, at the left, 40 columns by default, as wide as LazyVim's file tree. While there's a diff or details open, or another tab showing, or after `z`, gclic shows over the whole editor, and back in the sidebar once none of those holds. gclic decides, as it knows what it shows: it tells the plugin through `$NVIM` when that changes, and the plugin moves the one terminal buffer between the sidebar's split and a float. One buffer, not two gclics, so the selection, the tab and the undo history stay. A terminal takes the size of the smallest window it's in, so it's never in both: the split holds an empty buffer while the float shows, which keeps the code beside it from moving, and the float starts at the split's row and is as high. Over the whole editor the panes take the whole width with nothing open, as someone going there may want just that: wider panes. Beside a diff they take the columns in `$GCLIC_PANES_WIDTH`, which the plugin sets to the sidebar's width, as wide as a file tree, so they stay put as the diff opens; gclic on its own gives them a fifth. Never more than half, so a narrow editor leaves the diff room. Only the Repo tab's: the Review tab's comments are read in its list, which keeps its larger share. `z` only changes the size, never opens anything, so each thing has one key: from the sidebar it goes over the whole editor, there it zooms a diff and back as it does anywhere, and with nothing open, the biggest gclic gets, it goes back. Going there with `z` is a choice that lasts, so closing a diff then stays, whereas a diff opened from the sidebar takes gclic back when it closes. There's no `Z`: `esc` and `ctrl-g` already make it smaller. gclic knows the sidebar's width from `$GCLIC_SIDEBAR_WIDTH`, and until the plugin has resized it, it draws the panes as in the sidebar, so there's no frame of a diff squeezed into 40 columns, or of panes jumping wide on the way back. `ctrl-g` is gclic's own there, as going back to the sidebar means closing what it shows, and it asks the plugin to hide it from the sidebar. `o` opens the file beside the sidebar. The sidebar and a file tree take turns at the left, as both want that place: opening the sidebar closes the tree, and a tree opening hides gclic. neo-tree's and nvim-tree's windows are known by their filetypes; Snacks's explorer shares its filetypes with every Snacks picker, so it's known by Snacks's list of open explorers instead, and it closes a moment later, which the sidebar waits for so it opens at its own width. Terminal windows start without `wrap`, which lets the mouse scroll gclic's lines sideways even while the code has the focus, so the plugin sets it wherever gclic's buffer shows. In Neovim's sidebar gclic leaves out its own colour bar, as Neovim's shows. Without the plugin, gclic decides by its width alone: below 60 columns a diff or details take the whole width. `tests/nvim/sidebar.lua` checks the plugin end to end in headless Neovim with a real gclic: `nvim --headless --clean -l tests/nvim/sidebar.lua target/debug/gclic`.
- **Releases are built by dist, and gclic installs as other tools do.** A version tag builds gclic for macOS (Apple Silicon and Intel), Linux (x86_64 and arm64) and Windows, with dist (cargo-dist), which writes `release.yml` from `dist-workspace.toml`, publishes the builds on the GitHub Release with shell and PowerShell installers, and writes the Homebrew formula into `chuan97/homebrew-tap`. Windows has the PowerShell installer only: Scoop has no place in dist, and a bucket of gclic's own wasn't worth a hand-written publish job for the few who install gclic on Windows. Not on crates.io for now. Nothing is signed: Windows warns the first time, and Homebrew's installs don't meet Gatekeeper.
- **The Neovim plugin installs its own gclic.** The plugin is gclic's repo, so the `Cargo.toml` beside it says its version, and `lua/gclic/install.lua` fetches the release build of that version into Neovim's data folder, where the plugin looks first, after a `cmd` of the user's own. lazy.nvim runs `build.lua` at a plugin's root on installing and updating it, so the one spec in the README installs both and keeps them at the same version, which other plugin managers get with `:GclicInstall`. It needs curl and tar, which Windows 10 and later have too, its tar unpacking zips. The headless test installs from an archive it packs itself, through a `file://` address in place of GitHub's.
- **Saves in Neovim show at once.** gclic reads the repo every 10 s once idle, too slow for a sidebar that's watched but not typed into, and reading it more often would cost on large repos. Instead the plugin counts saves, along with returns to Neovim and `:!` commands, in a file named in `$GCLIC_SAVED`, and gclic, checking it on the same 500 ms tick as following, reads the repo when the count changes. That costs a small file read while nothing is saved. A count, not a time, so quick saves aren't lost to a file system's coarse times.
- **Stashes are listed and applied, not made.** `git stash` has the options for what to put in one, which a key couldn't improve on, so making one is left to `:git stash`. `:stash` lists them, and a stash shows in the Compare tab's view, as two refs do: underneath, it's a commit whose first parent is the commit it was made on, so its tracked changes are a diff from that parent, and its untracked files, in a third parent, are new against the empty tree. Applying puts everything back unstaged, as plain `git stash apply` does. Stashes are also in the graph, each just above its base as a commit with that one parent, which the lane layout draws as a short branch, in a muted colour, and only when its base is shown. Pop and drop need the stash's current name, `stash@{n}`, which shifts as stashes come and go, so they find it again by sha.
- **Switching repos starts the app afresh.** Every git call runs in a `Repo`, its root and git directory, made once per repo and given to every git call, whatever the process's working directory. `:cd` makes the new one and rebuilds the app state with it, keeping only how the user chose to show diffs. The old worker and fetch keep the old repo, so what they're still doing runs there. The old worker's thread ends once the old app drops it, and the fetch once it's done. gclic never changes its working directory: what the user runs, `:!` commands and editors, is started in the repo's root. The repos are found by reading folders, five deep, not inside a repo and not in hidden or dependency folders, which takes a few tens of milliseconds on a typical `~/Code`, so it runs on demand. The search folder stays the one gclic started with, the repo's parent or where gclic started outside a repo, so `:cd` lists the same repos wherever the user has switched to. `..` moves it up, for the rest of the session. `:cd name` skips the finder when the name can only mean one repo: an exact path or folder name, or the only fuzzy match.
- **A diff on screen takes `n`/`N`, `e` and `s` from any pane,** so its changes can be stepped through while browsing files, and from then on its active line shows, as that's where the user is. The graph's own `n`/`N` between commits only work with no diff open.
- **Commit details as a preview,** following the selected commit, rather than a popup.
- **Review comments go by the clipboard.** `gc` comments on a diff's line and `gC` on its whole file, the Review tab gathers the comments, and `y` copies them as one review, as plain text that can be pasted anywhere, to a person or a program, with nothing to install on their side. Hunk (hunk.dev) instead has a coding agent fetch the comments by running a command, through a local server, which also lets it reply to them; gclic could do the same later by keeping the comments in a file in `.git`. A comment keeps its line's text as well as its number, so it finds the line again when the file changes above it, and the copied review quotes the line for the same reason. Comments on the working tree belong to the file, not to its staged or unstaged diff, so staging doesn't lose them. Review is a tab, as Compare is, a place to gather comments rather than a different way of using gclic, and it only shows while there are comments, so `tab` cycles through two tabs the rest of the time. Comments aren't saved: they last until cleared or until gclic quits, which says how many would be lost. Ranges of lines aren't taken yet.
- **A change at a time, not a hunk or a line.** Inside a working-tree diff, `space` stages or unstages the change the active line is in, and `d` discards it after asking, the unit `n` moves by, so it works the same with the whole file shown. gclic writes a patch of that one change, as `git add -p` does when it splits a hunk, and git applies it: to the index, or in reverse to it for unstaging, or in reverse to the file for discarding. The hunk's other changes become context or are left out, as the side the patch goes to has them. Git checks the patch against that side, so one made before the file changed fails and changes nothing. A file whose diff is one change goes whole, as in the list, which also covers new and deleted files. Staged changes aren't discarded from their diff: unstaging comes first, so discarding only ever takes what isn't staged.
- **Undo keeps states, not operations.** `u` undoes a staging, an unstaging or a discard, and `ctrl-r` redoes it, where those are done: the Changes pane and inside a working-tree diff, so elsewhere a stray `u` can't undo what's out of sight, and the keys stay free for other panes, as in vim, a new step clearing what could be redone. Each step keeps what it touched before and after: the files' index entries, as `ls-files --stage` gives them, conflict stages included, or the files themselves, as blobs in git's object store. Undoing puts the before back, but only while the after is still there, so an edit made since, in gclic or elsewhere, is never lost to it; a step refused is dropped, and the next undo goes on. Keeping states rather than reversing patches makes whole files, new and deleted ones, binary files and conflicts all the same case. Only git's own operations are undone: an untracked file deleted was never in git, and keeping copies of them would make gclic a backup tool. Committing clears the steps, as unstaging what's committed would only confuse, and so does `:cd`, as the app starts afresh.
- **Comments are on a line or a file, not a hunk.** Hunks come from how the diff is drawn: showing the whole file makes it one hunk. A change, a run of changed lines, is where `n` lands, so a comment on a change is one on the line `n` lands on. `gc` works from the list beside the diff once `n` has shown the active line there, so commenting on changes doesn't need entering the diff. `gC` needs a diff on screen, so what's commented on is always in view.
- **`g` is a prefix, as in vim.** `gg` goes to the top, and `gc`/`gC` comment, `gc` being Neovim's comment key too. `c` already means commit or compare in the lists, so a plain key would have meant different things in different panes. While `g` waits, the hint bar shows what can follow it.
- **The hint bar leaves out the keys for moving.** `j`/`k`, `h`/`l` and `ctrl-d`/`ctrl-u` work everywhere and never change, so listing them only crowded out the keys that do.

## Considered and declined

- **Push, pull and fetch:** one command each with nothing to see. They need the network, can ask for credentials, and lead towards a complete client.
- **Switching worktrees inside gclic:** your shell and editor would stay in the old folder. The model is one terminal tab and editor window per worktree, which is how VS Code does it too, a window per folder.
- **A three-way merge editor:** resolving is for an editor. gclic shows the conflict and opens it in one. VS Code's merge editor works as `git mergetool`.
- **Refreshing on terminal focus,** and polling less out of focus: past refreshing by key presses it saves a few tenths of a percent, and support varies, Neovim's terminal included. Its gain would be a screen that's current the moment you come back, rather than on the first key (#77).
- **Manual pane resizing, a vim-style cursor in diffs, a fallback for terminals without the bead characters, a quick first highlighting pass, showing a diff3 base:** each deferred until it's actually missed.
